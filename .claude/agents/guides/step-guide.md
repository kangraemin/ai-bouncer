# Step 문서 작성 기준

step-N.md는 Lead/QA/Dev 세 역할이 순서대로 채워나가는 문서다. 각 역할의 작성 기준을 정의한다.

---

## Lead 작성 기준 (## 개발 내용 섹션)

Lead는 **무엇을 개발하는지**만 적는다. 어떻게 구현할지는 Dev가 plan.md를 참고해서 결정한다.

**작성 원칙:**
- 이 Step 완료 후 어떤 동작이 가능해지는지 동작 단위로 기술
- 선행 Step과의 의존 관계를 명시 ("Step N 완료 후 진행 가능" 등)
- 어떤 파일을 다루는지 범위를 명시 (파일 경로 포함)

**금지:**
- "파일 수정", "코드 추가" 수준의 추상적 기술 — 어떤 동작이 가능해지는지 기준으로 작성
- Before/After 코드 스니펫 — Dev가 plan.md 보고 결정
- 구현 방법/알고리즘 — Dev 영역

**예시 (✅ 올바른 기술):**
> bash-gate.sh 실행 시 SESSION_ID를 /tmp/.ai-bouncer-current-session에 저장하여, 이후 claim-active.sh가 이 값을 읽어 .active 파일에 기록할 수 있게 된다.

**예시 (❌ 잘못된 기술):**
> bash-gate.sh 파일을 수정한다.

---

## QA 작성 기준 (TC 테이블 + ## 실행출력 섹션)

QA는 **어떻게 검증하는지**를 구체적으로 정의한다. tc-guide.md의 기준을 따른다.

**TC 테이블:**
- TC 유형 컬럼 필수 (happy/BVA/regression/error/e2e)
- 기대 결과: 실제 출력값/반환값/상태변화를 명시. "정상 동작", "오류 없음" 금지.
- 검증 방법: 복붙해서 바로 실행 가능한 명령어. 수동 검증 금지.

**## 실행출력 섹션:**
- 실제 명령어 실행 후 출력 그대로 붙여넣기 (요약/편집 금지)
- 이 섹션이 비어있으면 plan-gate가 다음 step을 차단

**금지:**
- "사용자가 확인", "앱 재시작 후 확인" — QA가 직접 명령어로 실행할 수 없으면 TC로 인정 안 됨
- 실행 결과 없이 ✅ 기록

---

## Dev 작성 기준 (## 구현 내용 섹션)

Dev는 **무엇을 어떻게 변경했는지**를 diff 없이도 파악할 수 있게 적는다.

**필수 포함:**
1. 변경한 파일 경로 전부 나열
2. 각 파일에서 어떤 함수/클래스/로직을 추가·수정·삭제했는지 구체적으로
3. 구현 선택 이유: 왜 이 방식으로 했는지 (대안이 있었다면 왜 이걸 택했는지)
4. 빌드 명령어 + 실제 출력 결과

**금지:**
- "파일 수정함", "로직 추가함" 수준의 기술 — diff 없이 읽어도 변경 내용 파악 가능해야 함
- 빌드 결과 없이 "성공" 선언

**예시 (✅ 올바른 기술):**
```
hooks/bash-gate.sh (수정):
- 16번 줄 SESSION_ID 추출 직후에 저장 로직 추가:
  [ -n "$SESSION_ID" ] && echo "$SESSION_ID" > /tmp/.ai-bouncer-current-session
- 이유: claim-active.sh가 /tmp 파일에서 session_id를 읽기 위해 bash-gate가 먼저 저장해야 함
```

**예시 (❌ 잘못된 기술):**
```
hooks/bash-gate.sh 파일을 수정하여 session_id 저장 기능을 추가했습니다.
```
