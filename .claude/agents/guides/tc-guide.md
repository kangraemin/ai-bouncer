# TC 작성 및 검증 가이드

## TC 유형 정의

| 유형 | 키워드 | 정의 | 언제 사용 |
|------|--------|------|----------|
| Happy Path | `happy` | 정상 입력 → 기대 출력 | 거의 모든 Step |
| Boundary Value Analysis | `BVA` | 경계값 검증 (경계값-1, 경계값, 경계값+1) | 수치/길이/개수 경계가 있는 경우 |
| Regression | `regression` | 이전에 동작하던 TC를 재실행 — 깨지지 않았는지 확인 | 기존 동작에 영향 가능성이 있는 변경 |
| Error/Negative | `error` | 잘못된 입력, null, 타입 오류 → 올바른 에러 처리 | 외부 입력 검증, 예외 처리 |
| e2e | `e2e` | 전체 흐름을 실행하는 통합 테스트 스크립트 | Phase 완료 후 end-to-end 검증 |

**BVA 공식**: 경계값이 N이라면 `경계값-1`, `경계값`, `경계값+1` 세 케이스를 모두 검증한다.

**Regression TC**: "이전에 동작하던 시나리오를 그대로 재실행"이 Regression TC의 본질. 새로 추가된 코드가 기존 동작을 깨지 않았는지 확인.

**e2e TC**: 검증 방법에 `bash tests/e2e-xxx.sh` 형태 허용. 실행 가능한 스크립트 경로를 명시.

## TC 최소 기준 (Step당)
- happy, regression은 거의 모든 Step에 포함
- BVA는 경계가 있는 경우, error는 입력 검증이 있는 경우
- 갯수 최소치 없음 — 확실한 케이스만, 중복 금지

## TC 테이블 필수 컬럼
| TC | TC 유형 | 시나리오 | 기대 결과 | 검증 방법 | 실제 결과 |
- Step당 6컬럼 모두 채워야 함 (TC 유형 컬럼 필수)

## 검증 명령어 규칙
- 복붙해서 바로 실행 가능한 명령어여야 함
- `node -e "..."`, `python3 -c "..."`, `bash -c "..."` 등 인라인 실행 가능 형태
- 프로젝트 테스트 프레임워크 명령어도 가능 (pytest, jest 등)
- **Claude가 직접 실행해서 출력을 확인할 수 있어야 함**
- **"사용자가 확인", "앱 재시작 후 확인", "직접 열어서 확인" 등 수동 검증 금지**

## ✅ 찍기 전 체크리스트
1. 검증 명령어를 실제로 실행했는가?
2. 실제 출력을 step.md에 그대로 붙여넣었는가?
3. 기대 결과와 실제 출력이 일치하는가?
→ 3개 모두 YES일 때만 ✅. 하나라도 NO면 ❌.

## 경계값 예시
- 숫자: 0, 음수, 최대값, NaN, Infinity, 소수점
- 문자열: 빈 문자열, 공백만, 특수문자, 매우 긴 문자열, 유니코드
- 배열/리스트: [], [1개], 중복 요소, 매우 긴 배열
- 객체: {}, null, undefined, 필수 필드 누락, 추가 필드
- 파일: 존재하지 않는 경로, 빈 파일, 권한 없는 파일

## TC가 약한 패턴 (이런 TC는 반려됨)
- "정상 동작 확인" — 입력값/기대결과 없이 추상적 기술
- "에러 없이 실행됨" — 출력 내용 검증 없음
- "UI가 잘 보임" — 자동 검증 불가
- "앱 재시작 후 확인", "직접 열어서 확인", "사용자가 확인" — 수동 검증은 TC가 아님
- 동일 시나리오 변형만 3개 — 경계값/에러 없음

## 자동화 불가 TC 처리 방침
UI 클릭, 앱 재시작 등 자동화가 어렵다면:
1. CLI 플래그, 환경변수, 로그 출력 등으로 간접 검증 방법을 먼저 찾는다
2. 그래도 불가하면 해당 기능을 테스트 가능한 단위(함수/모듈)로 분리하여 단위 테스트로 검증
3. "사용자가 확인해주세요" 형태로 TC를 작성하지 않는다 — TC 작성자(Claude)가 직접 검증할 수 없으면 TC로 인정 안 됨
